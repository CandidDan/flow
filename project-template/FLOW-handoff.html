01 — Why this exists

The friction was the handoff, not the tools

Working between Cowork and Claude Code, the pain wasn't either tool — it was the seam. A spec written in one context had to be physically carried to the other: copy, paste, re-brief. Every handoff was a snapshot lugged across a gap.

The goal was a workflow where you occupy three seats deliberately — inspirator (you decide what matters), validator (you approve the result), and sometimes worker — while Claude Code gets on with the building without you holding it up. That only works if the spec stops being a snapshot and becomes live shared state both sides read and write. Kill the clipboard, and the seam disappears.

Flow is that shared state plus the contract around it. The promise it protects: across any project, on the happy path your job collapses to two touchpoints — approve the spec going in, approve the PR coming out. Two paths deliberately hand a third moment back to you when the work earns it: a kickback (you want changes on a PR) and a blocked task (the worker hits a decision that isn't its to make). Those aren't leaks in the promise — they're the system refusing to guess on your behalf. Everything else runs on its own.

02 — The shape

Four seats, one loop

You
Inspirator + validator. Decide what matters; approve spec & PR. Never displaced.
Cowork
Orchestrator. Turns direction into ready-to-work tasks; watches the board.
Claude Code
Worker. Pulls a ready task, builds it, clears the gate, opens a PR.
The gate
QA, security & code-review agents + CI. Nothing reaches you un-vetted.

The distinction that does the work: you own what and whether; Cowork owns decomposition; Code owns how. The orchestrator never invents priorities, and the worker never widens scope. Authority stays where it belongs at every layer.

03 — Architecture

Data underneath, views on top

The system separates the machine-to-machine layer (clean data, diff-friendly, written and read by agents) from the human-facing layer (rich HTML, read and manipulated by you). The two camps in the markdown-vs-HTML debate were never arguing about the same layer — Flow assigns each its proper format.

The store is the centre of gravity. Views render it, the worker drives it, the protocol governs it, the gates guard the exit, and the flightdeck reads across many copies of it.

One consequence makes the store work under parallel sessions: it splits into two planes. Task state lives on main — claiming, hand-off and blocking are tiny metadata commits every session can see at once. Feature code never touches main; it goes on a branch and through the gate to a PR. That separation is what lets git itself be the coordinator (next section), with no lock file and no daemon.

04 — The loop

From a sentence of direction to a merged PR

Status moves one direction only. Your two happy-path touchpoints sit at the ends; the middle runs unattended. The two dashed paths — kickback and blocked — are where the loop hands a moment back to you on purpose. A fresh Code session per task, never one long thread, keeps quality from rotting across a backlog.

The unlock for "let Code get on without holding things up" isn't speed — it's readiness. Autonomous work stalls on under-specified tasks and bounces back to ask. So the orchestrator's real product is a task that's ready: scoped, with observable acceptance criteria and a machine-checkable definition of done. Get that right and the loop runs itself between your touchpoints.

Many of these loops run at once. The "one branch" in the diagram is per task, not per project — the queue runner can fan out several sessions. They don't collide because the store, not a lock, coordinates them: claiming a task is an atomic commit-and-push to main and first push wins; a rejected push means another session claimed it, so this one rebases and picks the next. Each task also declares the file globs it touches, so a session skips any ready task that overlaps something already in progress. Keep tasks small and disjoint and the fan-out is free.

05 — The gate

Quality on every project, regardless of stack

"Test coverage, QA and security on every project whatever the tech" is enforced in four independent layers, so no single point of good behaviour is load-bearing:

  • Protocol — CLAUDE.md makes the Definition of Done non-negotiable. Its first clause is the real gate: every acceptance criterion has a test that proves its outcome. Build, lint, test and the coverage floor back that up; all three review agents must pass before a PR opens.
  • Config — .flow/config.yml is the one per-stack file. It names the project's test/lint/build/coverage commands and a coverage_min. The protocol is identical everywhere; only these commands differ — which is exactly what makes the gate universal across languages.
  • CI — flow-gates.yml reads those same commands and runs the gate on every PR. Enforcement isn't trust-based: no green CI, no merge.
  • Agents — qa-verifier (every acceptance criterion has a proving test, not just line coverage), security-reviewer (secrets, dependencies, authz, input validation + project focus areas), code-reviewer (correctness, scope adherence, maintainability).

Coverage is a floor, not the gate. It's a blunt, game-able number — lines executed, not behaviour proven — so it sits underneath the real check (qa-verifier's criterion→test mapping) as a backstop that stops coverage quietly collapsing, never as the thing that says "done." Sitting exactly at the floor proves nothing on its own.

The security agent's focus list in config is where project-specific scrutiny lives — RLS policies, OAuth token handling, secret storage — promoted to first-class checks rather than afterthoughts.

06 — Decisions for review

What was chosen, and why

The structure is downstream of a few deliberate calls. These are the ones worth poking at.

Local in-repo store, not Linearlocal-first

The contract (rules, work, outcome, acceptance) is load-bearing; the vehicle is swappable. A local store co-locates task, criteria, code and PR in one git history — and keeps the loop free of any third-party runtime dependency. The task file is the handoff.

Trade-off: a per-repo store fragments cross-project view, and markdown is a poor phone-glance. Both are answered below (flightdeck; HTML board). If single-pane-across-projects or mobile triage ever genuinely bites, the contract is the durable part — the same fields (rules, work, outcome, acceptance) map onto Linear, so the migration is real work but bounded, not a rewrite. The option stays open.

Markdown for the protocol, HTML for the viewsper-layer

The test is Thariq's: do you hand-edit it, or read-and-pass it? CLAUDE.md is tool-loaded config you barely read — markdown, where its one advantage (easy editing) still applies. The board, digests and this document are read and shared — HTML, where richness and shareability win. The machine-written task data stays clean data underneath.

Trade-off: two formats to hold in your head. But they map cleanly to two audiences (machine vs human), so the split is a feature, not overhead.

A template repo now, a plugin laterstaged

Identical per-project structure is what lets the master agent rely on the shape. A GitHub template gives every new project the protocol, gates, agents and board from commit one.

Trade-off: template copies drift the moment you improve the protocol or agents in one repo. Concrete trigger: by the third project on the template, lift the skills + agents into a Claude Code plugin so updates propagate without editing every repo — by then the shape is stable enough to centralise, and three diverging copies is where the back-port cost starts to bite. Until then the template is the simpler, right unit.

Parallel work coordinated by git, not a lockfirst-push-wins

Several Code sessions can run at once. Rather than add a lock file or a scheduler, the store does the coordinating: task-state commits live on main, claiming is an atomic commit-and-push, and the first push wins. A rejected push is the signal that someone else took the task — rebase and pick the next. Tasks declare a touches glob list, so a session skips any ready task overlapping one already in flight.

Two invariants keep the two planes from corrupting each other, and both are enforced in CI rather than trusted: the store is main-only — a feature branch carries code, never .flow/ changes, or its frozen snapshot of a task file would clobber main's newer state on merge (flow-gates.yml fails any PR that touches .flow/tasks/) — and PR events own the lifecycle: flow-status.yml flips a task to in_review on PR open and back to ready on close-unmerged; flow-done.yml flips it to done on merge. Workers hand-write only the claim (atomic, first-push-wins) and blocked (judgment). With the branch never touching the store, git's three-way merge always keeps main's version, on any platform, no merge driver required.

Trade-off: correctness leans on tasks being small and disjoint in what they touch — two overlapping tasks claimed at once will collide at PR-rebase time. That pushes work back onto the orchestrator to decompose cleanly, which is work the model already wants done for readiness. And the deeper honesty: these invariants (atomic claim, touches, main-only store, a merge workflow for done) are reimplementing in git what a real tracker gives you for free. The model works, but if you routinely run several sessions in parallel, that's the signal the Linear option is worth taking sooner rather than later. The failure mode stays safe either way: an unresolvable conflict becomes a blocked task surfaced to you, never a silent bad merge.

Triage proposes; labels carry authorityinbox lanes

GitHub Issues are the capture inbox — log raw bugs from anywhere, mid-flow, no ceremony. A scheduled sweep (flow-triage) drafts a full ready-task spec as a comment on each issue and labels it proposed; flipping the label to approved (one tap, phone-friendly) is what lets the next sweep create the task. Nothing enters the store un-approved — touchpoint 1 survives automation as a label flip. An auto-ok lane (human-applied, for the genuinely mechanical) skips the wait: authority exercised as per-lane policy. On the way out, flow-review adds a server-side Claude review independent of the worker's session, with Copilot code review recommended as an advisory second opinion for true model diversity.

Trade-off: more bot commits to main and more AI spend per item — and a Claude reviewing Claude shares model-family blind spots, which is exactly why the non-Anthropic advisory reviewer earns its place. The deeper one: every automated lane inches toward autopilot. Both workflows ship off by default (a repo variable enables them), and the merge stays human until the system has earned trust over a few dozen PRs.

The flightdeck reads; it never decidesthin lens

The cross-project layer aggregates every project's state into one "needs you now" digest, so running several projects in parallel doesn't mean holding five mental models. It recommends and surfaces — it never reprioritises or invents work. Direction stays yours at portfolio scale, same rule as inside a project.

Trade-off: none structural — projects don't depend on it, so it's removable without breaking anything. The risk is purely that an agent oversteps into deciding; the protocol forbids it explicitly.

07 — Deliberately left open

What's yours to set

These aren't loose ends — they're where the real per-project judgement lives. The protocol, gates and loop are fixed; the calls below are the ones that decide whether a given project's gate is meaningful, and no template can make them for you.

The five commands and the numbers in .flow/config.yml — install, build, lint, test, coverage plus the coverage floor and the security focus list. The commands are mechanical; the floor and the focus list are judgement. A floor set too low is theatre, and the focus list (RLS, OAuth, secret storage…) is where this project's real risk gets promoted to a first-class check. This is the one genuinely per-stack file and the most consequential thing you'll fill in.
The toolchain setup line in .github/workflows/flow-gates.yml — the single irreducibly stack-specific CI step (node/python/go/…), marked in the file.
The board write-back is now wired, not left to you. Edits on the board no longer round-trip through your clipboard: "Apply edits" produces .flow/board-edits.json and the committed .flow/bin/apply-board-edits.mjs patches only the status/priority lines of the matching task files — the single canonical writer, so the files stay the source of truth and every change is a reviewable git diff. One honest caveat on the "straight into the project" path: the File System Access API that writes the file in place is Chromium-only and won't run from a file:// page, so for most setups the real flow is download the JSON → run the script. Still no clipboard, just not a silent direct write everywhere.
08 — Operating it

When the loop stalls, and what it costs

A foundation has to say how you debug it and what running it costs, or it isn't one. Both answers fall out of the same property: there's no hidden state. The store is files in git, so git log -- .flow/tasks/ is the whole audit trail — who claimed what, when, and why anything blocked.

When something feels stuck

  • A stuck worker — a task sitting in in_progress with no branch activity is the context-rot / crashed-session smell. The stale-task sweep surfaces it; recovery is to reset it to ready (clear owner) and let a fresh session re-claim it.
  • A stalled review — in_review too long means a PR is waiting on you; the portfolio digest leads with these so they don't rot silently.
  • A failed gate — the PR's flow-gates check names the failing command or agent; the agent verdicts land on the PR and kickbacks land in the task's notes. Read CI logs, then the verdict, then the diff. One gate failure isn't a code problem: "this PR modifies .flow/tasks/" means a state change leaked onto the branch — move it to a commit on main and drop it from the branch.
  • A blocked task — blocked_reason says why. It's a decision waiting on you, not a bug: answer it, set the task back to ready.
  • Branch protection on personal repos — validated live: required checks block red-gate merges, but personal repos can't exempt the Actions bot, so protection also blocks the store-sync pushes. Run protection-off on personal repos (the gate still reports on every PR; you're the only merger); on an org, use a Ruleset with the Integration as bypass actor.
  • A task stuck at in_review after its PR merged — done is written by flow-done.yml on merge, reading the id from the branch name. If a task didn't flip, the branch name didn't match flow/<id>-…; the workflow log says so.

What the gate costs

Up to three review agents plus a CI run per PR — and that spend is the point. The agents review the diff and its blast radius, not the whole repo, so per-PR cost stays bounded as the codebase grows; they run on sonnet (hard to fool, cheap to run every PR); and security-reviewer earns its keep on auth / input / dependency diffs while having little to chew on in a pure styling change. CI minutes scale with PR volume, not project size — and small, disjoint tasks (what concurrency already wants) are also the cheapest to gate. The expensive failure mode is a slipped PR you have to unwind, not an agent invocation.
