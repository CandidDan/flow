Flow

Delegate the work, not the watching.

Flow turns Claude into a software team you supervise at exactly two points — the spec going in and the pull request coming out. Everything in between runs itself, and nothing reaches you until it’s genuinely done.

How it works Why it’s different

AI can write code. It can’t be trusted to ship it — yet.

So you babysit: re-reading every diff, re-running every check, re-feeding context. The bottleneck was never the model’s ability. It’s the missing system that makes “done” actually mean done — and without it, autonomy quietly collapses back into supervision.

Flow is that system. You approve the spec and the PR. The rest is the machine’s job.

How it works

A thin protocol that lives inside your repo — not another platform to log into.

01 — SPEC

Write the task as a contract

You and Claude turn direction into a real spec: observable acceptance criteria, the exact files it may touch, and the boundary. Vague isn’t allowed — a task is only “ready” when a fresh session could finish it with no further questions.

02 — BUILD

A worker builds behind a hard gate

A fresh Claude Code worker claims it, builds on a branch, and cannot open a PR until every criterion has a passing test that proves it — plus security review, code review, and the full build / lint / test / coverage.

03 — MERGE

You review and merge

You read the PR — criteria ticked, each with the test that proves it — and merge. Two touchpoints, start to finish. Several workers run in parallel without colliding, coordinated by nothing but git.

Why it’s different

Most tools help an agent write code faster. Flow is about making its “finished” trustworthy.

Done means done

No PR opens on “looks good to me.” Every acceptance criterion is mapped to a test that proves it, checked by name before the gate lets the PR through.

The model refuses to guess

Hit an under-specified spot or a real decision, and the worker blocks and asks instead of fabricating. A block is integrity, not failure.

Plain files, not a platform

Your tasks are Markdown in your own repo, on main. Nothing to log into, nothing to migrate off, no lock-in. The board is just a generated view.

Coordinated by git alone

Many workers at once. Claiming a task is an atomic first-push-wins commit; a touches list keeps two of them out of the same files. No daemon, no lock server.

It hardens itself

Every incident becomes a permanent guardrail. The system gets safer the more it’s used — failures turn into checks, not folklore.

Stack-agnostic

The same protocol runs a static site and a full app. Only a small per-project config and the project’s own context file differ.

Every failure becomes a guardrail

Flow wasn’t designed on a whiteboard — it was hardened by getting burned, and each scar became a rule the system now enforces for you.

A parse error in an unchecked file silently dropped messages for ~7 days.
→ The gate now refuses to merge any source tree it doesn’t actually parse.
A worker did all the work, then ended its turn without opening the PR.
→ PR creation moved off the model and onto a workflow — a stall can’t strand the work.
A task was written but never pushed, so a cloud worker couldn’t see it.
→ A store check fails loudly the moment a task exists on disk but not on main.

Who it’s for

Solo builders and small teams running several projects at once who want to hand real work to AI without losing the thread — and want the safety to come from the system, not from their own vigilance. If you already use Git and CI, you already have everything Flow needs.
