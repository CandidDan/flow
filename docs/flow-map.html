Flow — System Map

One picture of the moving parts: the layers, who controls what, and the path a piece of work takes. The promise underneath it all — you approve the spec and the PR; everything between runs itself.

The layers

Engine GitHub Actions — per repo, calling canonical @v1

The automation. Each is a thin caller; the logic lives in canonical. AI ones are gated by FLOW_AI.

Local agents your Mac

Keep the local picture current so Cowork never reads stale state.

Two touchpoints (the orange steps): the spec in, the PR out. Side paths that add a touchpoint only when reality demands it: a kickback (you ask for changes) and a blocked task (the worker refuses to guess). flow-recover auto-rescues a stalled task; flow-triage feeds GitHub issues into the ready queue; the flightdeck shows all of it across projects.

What controls what

RelationshipHow
Repos → canonicalThin workflows uses: CandidDan/flow/_flow-*.yml@v1. Fix canonical once, every repo on @v1 gets it. No local copy to drift.
Canonical → repos (updates)flow-sync opens an adopt PR (Dependabot-style). A FLOW_VERSION drift-check (planned) flags a repo that's behind — detect & propose, never silent self-update.
New repo → canonicalSeeded from project-template/ (INIT/RETROFIT), then registered in flightdeck/projects.yml.
Store ↔ codeTwo planes: task-state changes commit straight to main; feature code goes branch → PR → gate. store-guard + touches-guard enforce it.
Orchestrator ↔ storeReads origin/main (fresh via flow-fetch); writes tasks to main; views regenerated by the scheduled task.
